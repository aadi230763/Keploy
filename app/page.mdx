# Build Your First Keploy Test Suite for a Go API

A beginner-friendly walkthrough of recording and replaying API tests with Keploy, using a real Go application and MySQL.

---

## Start here

This tutorial is for developers who are comfortable running commands in a terminal and have seen a little Go, but have **never used Keploy** or any tool that generates API tests automatically.

You won't write a single test by hand. Instead, you'll run a small Go API, use it the way a real client would, and let Keploy turn those interactions into a test suite you can re-run at any time.

By the end, you will have:

- a Go URL-shortener API running against MySQL
- a folder of **test cases** that Keploy generated from real requests
- a set of **mocks** that let those tests run without depending on the database's current contents
- a passing test run, and a clear picture of *why* it passed

Throughout the page, you'll see a few kinds of blocks. Here's how to read them:

- **Terminal** blocks (with a `$` prompt) are commands to run. The copy button copies the command without the prompt.
- **Output** blocks (dashed border) show what you should expect to see. You don't run these.
- **Colored callouts** explain *why* a step exists, flag common mistakes, or give you a checkpoint before moving on.

## What you'll build

You'll take a small Go URL-shortener API, point Keploy at it, send a few real HTTP requests, and watch Keploy turn those requests into a fully automated test suite — without writing a single test by hand.

The application exposes three endpoints:

| Endpoint | What it does |
| --- | --- |
| `POST /create` | Shorten a URL |
| `GET /all` | List every stored link |
| `GET /links/:id` | Redirect to the original URL |

You'll exercise all three, and Keploy will capture each interaction — including the MySQL queries the app makes behind the scenes — so you can replay them later as deterministic regression tests.

You don't need to understand how the Go code works internally. For this tutorial, the app is a black box: requests go in, responses come out, and it talks to MySQL in between.

## What is Keploy?

Keploy is a testing tool that **creates API tests by watching your application run**.

Normally, writing an API test means deciding up front what request to send, what response to expect, and how to fake the database so the test is repeatable. That's a lot of work before you've checked anything.

Keploy flips that around. You run your app *through* Keploy and use it normally. While you do, Keploy sits in the middle and records:

- every **HTTP request** that comes into your app, and the **response** your app sent back
- every call your app makes to its **dependencies** — in this tutorial, the MySQL queries and their results

Later, Keploy can **replay** those recorded requests against your app and check that the responses still match.

A few terms you'll see throughout:

| Term | What it means here |
| --- | --- |
| **Record mode** | Keploy launches your app and captures real traffic. Started with `keploy record`. |
| **Test case** | One recorded HTTP request plus the response the app returned. Saved as a YAML file. |
| **Mock** | A recorded dependency interaction (such as a MySQL query and its result) that Keploy plays back during tests instead of calling the real dependency. |
| **Test mode** | Keploy launches your app, replays the recorded test cases, and compares responses. Started with `keploy test`. |

<Callout type="why" title="What makes this different from normal testing">

Instead of *inventing* requests and expected responses up front, you use the application normally and let Keploy *observe* what happens. Tests are grounded in real behavior, not assumptions.

</Callout>

## The mental model

Before touching the terminal, here's the whole idea in six steps. Every command in this tutorial serves one of them.

1. **Start the Go application** — through Keploy, so Keploy can see its traffic.
2. **Send API requests** — with `curl`, exactly like a real client would.
3. **Keploy records those interactions** — both the HTTP traffic and the MySQL queries.
4. **Keploy generates test cases** — one YAML file per request, plus mocks for the database.
5. **Replay the generated tests** — Keploy sends the same requests again and serves MySQL results from the mocks.
6. **Verify that the application behaves consistently** — if the responses match the recording, the tests pass.

Steps 1–4 are the **record phase**. Steps 5–6 are the **replay phase**. Keeping those two phases separate in your head is the single most useful thing to take from this tutorial.

## Step 1: Get the sample application

Keploy maintains a repository of sample apps. We'll use `mux-mysql`, a URL shortener written in Go with the Gorilla Mux router and a MySQL database. Using a known-good sample means that if something goes wrong, it's almost certainly the environment — not the app.

Clone the repository and move into the application's directory:

```bash
git clone https://github.com/keploy/samples-go.git
cd samples-go/mux-mysql
```

<Callout type="warning" title="Stay in this directory">

Every remaining command in this tutorial — Docker, Go, and Keploy — runs from `samples-go/mux-mysql`. If you open a new terminal later, `cd` back here first.

</Callout>

---

## Step 2: Start MySQL

The app stores its short links in MySQL, so the database has to be running before the app can start. Rather than installing MySQL on your machine, you'll run it in a Docker container. The sample repo already includes a Docker Compose file that defines it.

Start the database in the background (`-d` means "detached", so you get your terminal back):

```bash
docker compose up -d
```

MySQL takes a few seconds to initialize after the container starts. Follow its logs to know when it's ready:

```bash
docker compose logs -f db
```

Look for a line containing:

```text
ready for connections
```

Once you see it, press <kbd>Ctrl</kbd> + <kbd>C</kbd> to stop following the logs. This only stops the log viewer — MySQL keeps running in the background.

### Tell the app where MySQL is

The Go application doesn't have its database address hard-coded. It reads it from an environment variable called `ConnectionString`. Set it now:

```bash
export ConnectionString="root:my-secret-pw@tcp(localhost:3306)/mysql"
```

This says: connect as user `root` with password `my-secret-pw`, over TCP to `localhost:3306`, and use the `mysql` database.

<Callout type="why">

The Go application reads `ConnectionString` from the environment to connect to MySQL. If this variable is missing or wrong, the app will crash on startup. Environment variables only exist in the terminal where you set them — we'll come back to this in [Troubleshooting](#troubleshooting).

</Callout>

<Callout type="checkpoint">

Before moving on, verify:

- Docker is running
- The MySQL container is healthy on port `3306`
- `ConnectionString` is exported in your terminal session

</Callout>

---

## Step 3: Build the Go application

Keploy needs an application to launch. Here you compile the Go source into a single executable file called `main`, which is what you'll hand to Keploy in the next step.

```bash
go build -o main -cover
```

- `-o main` names the output file `main`.
- `-cover` builds the binary with Go's coverage instrumentation enabled.

Confirm the binary was created:

```bash
ls -l main
```

You should see a file named `main` in the listing.

<Callout type="why" title="Why build instead of go run?">

Keploy instruments the running process to intercept network traffic. On macOS, giving Keploy a single compiled binary (`./main`) is more reliable than letting `go run` create a temporary process. This was one of the first things I had to learn — `go run .` works for development, but Keploy needs the actual executable.

</Callout>

<Callout type="warning" title="Don't start ./main yourself">

It's tempting to run `./main` now to check that it works. If you do, stop it before continuing. In the next step, Keploy launches the app itself — and if another copy is already holding port 8080, Keploy's copy can't start.

</Callout>

---

## Step 4: Start Keploy in record mode

This is where Keploy enters the picture. Instead of running the app directly, you start it *through* Keploy. That lets Keploy position itself between the outside world and your app, so it can see every request coming in and every database query going out.

```bash
keploy record -c "./main"
```

- `record` puts Keploy in record mode.
- `-c "./main"` is the command Keploy should use to launch your application.

Keploy launches the application as a child process and begins intercepting all network traffic — both the incoming HTTP requests to the API and the outgoing MySQL queries.

You should see output similar to:

```text
Keploy agent is ready to record test cases and mocks.
Starting Application : {"executing_cmd": "... ./main"}
```

While recording, the traffic flows like this:

```flow
Your curl requests
       ↓
     Keploy (intercepting)
       ↓
   Go application
       ↓
     MySQL
```

Keploy sits between you and the app, and between the app and its database. It watches everything, but it doesn't change anything — the app behaves exactly as it would without Keploy.

<Callout type="warning" title="Keep this terminal open">

Don't close this terminal or press <kbd>Ctrl</kbd> + <kbd>C</kbd> yet. The application is running inside Keploy's recording session, and everything you do in the next step will be captured.

</Callout>

## Step 5: Exercise the API

Now you act as a client of the API. **Every request you send in this step becomes a test case**, so think of this as "demonstrating how the app should behave."

Open a **second terminal window** and `cd` into `samples-go/mux-mysql`. Leave the Keploy recording session running in the first.

All of the requests below use `curl -i`. The `-i` flag prints the response's status line and headers along with the body, so you can see exactly what the API returned.

### 5.1 Check the current links

Start by asking for every stored link. This is a simple read request, and it confirms that Keploy is passing traffic through to the app.

```bash
curl -i http://localhost:8080/all
```

If the database is empty, you'll get an empty list. That's expected — the important thing is that the request reaches the application and returns a response.

### 5.2 Create a link

Next, write some data. This request asks the API to shorten `https://github.com`. The app will insert a row into MySQL, and Keploy will record both the HTTP exchange and that database write.

```bash
curl -i -X POST http://localhost:8080/create \
  -H "Content-Type: application/json" \
  -d '{"url":"https://github.com"}'
```

The API should return a response containing the new link, for example:

```text
/links/1
```

The exact ID may differ on your machine. Make a note of it — you'll use it in 5.4.

### 5.3 Retrieve all links

Ask for all links again. This time the answer should be different, because you just added one.

```bash
curl -i http://localhost:8080/all
```

You should see the link you just created in the response. This confirms the app can write to and read from MySQL.

### 5.4 Follow the generated link

Finally, use the short link. This is what the app is actually for: turning a short path back into the original URL.

```bash
curl -i http://localhost:8080/links/1
```

Replace `1` with whatever ID your app returned in 5.2. You should see a redirect:

```text
HTTP/1.1 307 Temporary Redirect
Location: https://github.com
```

A `307` status with a `Location` header means "go to this other URL instead." That's the shortener working.

<Callout type="why" title="What just happened behind the scenes">

For each of these four requests, Keploy captured the full HTTP request and response, and also recorded every MySQL query the app made while handling the request. All of this is written to disk as YAML files.

</Callout>

---

## Step 6: Stop recording

You've shown Keploy enough behavior to build a test suite. Now tell it to stop watching so it can finish writing everything to disk.

Go back to the **first terminal** (where Keploy is running) and press <kbd>Ctrl</kbd> + <kbd>C</kbd>.

Keploy will finish writing the recorded data and exit. You should now have a `keploy` directory in your project:

```tree
keploy/
├── reports/
└── test-set-1/
    ├── config.yaml
    ├── mappings.yaml
    ├── mocks.yaml
    └── tests/
        ├── get-all-1.yaml
        ├── get-links-by-id-1.yaml
        └── post-create-1.yaml
```

Each file in `tests/` corresponds to one of the API requests you sent. The `mocks.yaml` contains the recorded MySQL interactions. The exact filenames may vary depending on what you recorded.

## Step 7: Understand what Keploy created

Before replaying anything, it's worth understanding what's in that folder. Keploy generated two kinds of artifacts.

### Test cases

A test case captures an HTTP request and the response the app returned. Each one maps back to a request you sent in Step 5:

| Request you sent | Test case file |
| --- | --- |
| `POST /create` | `post-create-1.yaml` |
| `GET /all` | `get-all-1.yaml` |
| `GET /links/1` | `get-links-by-id-1.yaml` |

When you replay, Keploy sends each recorded request to the app again and compares the new response to the one stored in the file.

### Dependency mocks

`mocks.yaml` captures what happened between the app and MySQL during each request. During replay, Keploy uses these mocks instead of hitting the real database.

The remaining files, `config.yaml` and `mappings.yaml`, are supporting files Keploy uses to organize the test set. You don't need to open or edit them for this tutorial.

### Why mocks matter

Imagine your app runs a `SELECT * FROM links` query while handling `GET /all`. During recording, Keploy sees that query and the result MySQL returned.

During replay, Keploy intercepts the same query and returns the *recorded* result — so the test doesn't depend on what's currently in the database. This makes tests repeatable even if the database is empty or has changed since the recording.

<Callout type="why" title="This is the key insight">

Keploy doesn't just test HTTP responses. It records the full dependency graph — HTTP in, database out — and replays the whole interaction deterministically.

</Callout>

## Step 8: Replay the recorded tests

This is the payoff. You'll ask Keploy to start the app again, send it the same requests you recorded, and check whether it still responds the same way.

The app still reads `ConnectionString` on startup, so make sure it's set in the terminal you're using. If you're in a new terminal or aren't sure, set it again:

```bash
export ConnectionString="root:my-secret-pw@tcp(localhost:3306)/mysql"
```

Then replay:

```bash
keploy test -c "./main"
```

It's the same `-c "./main"` launch command as before, but `test` instead of `record`. Keploy will:

1. start the application again
2. replay each recorded request
3. answer the app's MySQL queries from the recorded mocks
4. compare the actual response to the recorded snapshot
5. report whether each test passed or failed

You should see individual results:

```text
post-create-1        passed
get-all-1            passed
get-links-by-id-1    passed
```

---

## Step 9: Verify the result

When the run finishes, Keploy prints a summary. In my run, Keploy reported:

```text
Total tests: 3
Passed: 3
Failed: 0
```

And:

```text
All 3 test(s) passed across 1 test-set(s).
Suite is green and dependency-free.
```

That's the result we want. **Passed** means that for every recorded request, the app returned the same response it did during recording. **Dependency-free** means the run relied on the recorded mocks rather than on what's currently stored in the database.

Three real API interactions have become three repeatable, automated tests — with dependency mocks — and zero test code written by hand.

## Troubleshooting

These are real issues I encountered while running this quickstart. Each one shows the error you'll see, what causes it, and how to fix it.

### Error: address already in use

```text
listen tcp4 0.0.0.0:8080: bind: address already in use
```

**Cause:** the Go application is already running on port 8080, and you tried to start another copy through Keploy.

**Fix:** stop the existing process first. Don't run `./main` separately and then ask Keploy to start it again — let Keploy be the one to launch the application:

```bash
keploy record -c "./main"
```

### Error: Connection string empty

```text
Connection string empty
```

**Cause:** the terminal where you're running the Keploy command doesn't have the `ConnectionString` variable set.

**Fix:** export it again in the same terminal:

```bash
export ConnectionString="root:my-secret-pw@tcp(localhost:3306)/mysql"
```

<Callout type="why" title="Why this catches people off guard">

Environment variables belong to a terminal session. Setting a variable in Terminal A doesn't make it available in Terminal B. If you opened a new tab to run `keploy test`, you need to export the variable again.

</Callout>

### Error: ./main: No such file or directory

```text
sh: ./main: No such file or directory
```

**Cause:** the compiled binary doesn't exist in the current directory.

**Fix:** make sure you're in the `mux-mysql` directory and build again:

```bash
go build -o main -cover
```

### Error: Go cannot find a main module

```text
go: cannot find main module
```

**Cause:** you're probably running Go commands in the wrong directory. This tutorial involves two separate projects:

| Project | Directory |
| --- | --- |
| Go application | `samples-go/mux-mysql` |
| Documentation website | `keploy-devrel-assignment` |

**Fix:** run Go commands like `go build` and Keploy commands like `keploy record` from the **Go application directory**, not from the Next.js project.

## What I learned from running this

The most useful part of this exercise wasn't getting three tests to pass. It was understanding the mental model behind Keploy.

### 1. The application must actually work first

Keploy can't record an application that fails to start. Before you add Keploy to the mix, make sure the app runs normally, can connect to its database, and responds to requests. Keploy observes a working application — it doesn't fix a broken one.

### 2. Port ownership matters

If the application is already running on port 8080, starting another copy through Keploy will fail. This caught me during my first attempt. The fix is simple: stop the existing process before starting it through Keploy.

### 3. Environment variables don't follow you between terminals

The recording terminal and the test terminal can be different processes. If the test terminal needs `ConnectionString`, you need to set it there too. This is basic shell behavior, but it's easy to forget in the middle of a tutorial.

### 4. Recording is not the same as testing

This was the biggest conceptual shift. During recording, Keploy simply watches. During replay, Keploy actively compares. These are two distinct phases with different goals:

- **Record** → create the test material from real behavior
- **Test** → replay that material and verify nothing has changed

### 5. The tests are grounded in reality

Instead of starting with *"How do I write three test cases?"*, the workflow starts with *"How does my application actually behave?"* — and then Keploy turns those real interactions into tests. For someone new to API testing, this is a much more approachable starting point.

## Final takeaway

Keploy lets you start with real API behavior and turn it into repeatable, automated tests — without writing test code, without managing database fixtures, and without manually constructing expected responses.

The workflow is:

```flow
Run → Record → Generate → Replay → Verify
```

If you can use `curl`, you can create a Keploy test suite.

Before calling this tutorial complete, verify:
